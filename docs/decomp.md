# 巴利詞的多階拆分（decomp）

> 目標：讓**詞自己帶著拆分信息**——`dhammacakkappavattana` 不是一整團，而是
> `dhamma + cakka + pavattana`；而 `pavattana` 如果本身還能拆，就再拆下去
> （`盟 = 明 + 皿`、`明 = 日 + 月`，而不是一次拆成 `日 + 月 + 皿`）。
>
> 這份只做**從 pwa 出發**的多階表（2026-11-02 起的方向：先不看經文）。
> 經文那邊的補充表見 §5。

## 1. 檔案與指令

```powershell
cd D:\2026\sz
bun run src/decomp/pwa-tree.ts     # 40 秒；記憶體友善（不快取 pwa）
```

| 檔 | 內容 | 大小 |
|---|---|---|
| `data/cs-decomp/pwa-tree.tsv` | **多階樹**（只收深度 ≥ 2 的 105,620 個詞） | 7.5 MB |
| `data/cs-decomp/pwa-atoms.tsv` | 全部原子 ＋ 出現次數 ＋ 詞幹 | 6.3 MB |
| `data/cs-decomp/pwa-alphabet.tsv` | 前 4,096 個原子（可當「一字元」字母表） | 0.3 MB |
| `data/cs-decomp/pwa-summary.txt` | 一行式摘要（給人快速看） | 小 |
| `out/pwa-tree-all.tsv` | 全部 956,729 個詞形的樹（大檔，不進版控） | 38 MB |

樹的字串寫法：`a[b|c]|d` ＝ 第一層是 a、b、d，其中 b 再拆成 b、c。
例：

```
abahumānakāraṇaṃ  2  a | bahumāna[bahu|māna] | kāraṇaṃ
pañcakaṅgoti      2  pañcakaṅgo[pañca|aṅgo] | iti
uttarāsaṅgaekaṃsakaraṇādīsu  2  uttarāsaṅga[uttara|āsaṅga] | ekaṃsa | karaṇa | ādīsu
```

## 2. 結果（956,729 個 pwa 詞形，≥3 字母）

| 深度 | 詞形數 | 佔比 | 意思 |
|---|---|---|---|
| 0 | 169,333 | 17.7% | 原子（pwa 認為不能再拆） |
| 1 | 681,776 | 71.3% | 拆一次（最常見） |
| 2 | 103,253 | 10.8% | 拆兩層 ← **多階真的用得上** |
| 3 | 2,342 | 0.2% | |
| 4 | 25 | 0.003% | |

- 平均每個詞 **2.51** 個原子。
- 原子 **256,387** 個；把 `dhamma／dhammā／dhammaṃ` 這種收成詞幹後 **130,942** 個。
- 詞件不是 pwa 詞形的：**205,227 / 2,117,517（9.7%）**——這是「抓大放小」要放掉的部分，見 §4。

## 3. 找出來的規律

1. **尾巴幾乎都是「附詞」**。最常見的結尾詞件：
   `iti(90,318) eva(28,880) api(26,552) ca(14,811) vasena(13,404) pi(10,975) ti(9,204)`。
   光是 `iti` 一種就佔 9.4% 的詞形——pwa 把 `…nti`、`…mīti` 這種連聲都拆成「詞＋iti」。
   → **附詞（ca／iti／eva／api／pi／vā）應該獨立一層**，不要跟前面的詞混在一起。
2. **開頭幾乎都是前綴或限定詞**：`a(26,982) sa(7,854) mahā(7,083) an(6,717) na(6,562)
   eka(6,278) sabba(6,057) su(5,373)`。`a-`／`an-`／`na-` 是否定前綴，`sa-`／`su-`／`du-`
   是同族前綴，`mahā-`／`eka-`／`sabba-` 是限定成分。
   → 前綴本身是「單音節或雙音節的封閉集合」，很適合當第一層。
3. **深度只到 2**。pwa 的拆法本身很淺：`cakka`、`kāraṇaṃ` 這種它不再拆（雖然詞源上
   `kāraṇa = kar + aṇa`）。所以要「拆到一個字符」，pwa 不夠，得再往下接**詞綴層**。
4. **9.7% 的詞件是壞的**，幾乎都是連聲把字吃掉或加倍：
   `dvattiṃsa → dva|ttiṃsa`（`ttiṃsa` 不是詞）、`puññaphalañca → puññaphala|ca` 沒問題，
   但 `…añca` 這種會被寫成 `…aṃ|ca` 或 `…añ|ca`。**不要為了這 9.7% 改規則**。
5. **原子裡有一批「不是詞」的碎片**：`a`（否定前綴）出現 35,410 次、`sa` 10,446 次、
   `an` 8,457 次、`na` 7,697 次——它們是前綴，不是自由詞。設計字母表時要把它們跟前綴層對齊。

## 4. 「一個字符」的算術（重要）

如果目標是「**每個因子剛好一個字符**」，那字母表要多大？用原子出現次數算：

| 字母表大小 | 覆蓋原子出現次數 |
|---|---|
| 10 | 12.7% |
| 32 | 18.9% |
| 64 | 23.8% |
| 128 | 30.3% |
| 256 | 37.7% |
| 512 | 45.7% |
| 1,024 | 54.0% |
| 2,048 | 62.3% |
| 4,096 | 70.1% |
| 8,192 | 76.9% |
| 16,384 | 82.5% |

- 要 **100%** 一原子一字符，需要 **256,387** 個字符（收成詞幹也要 130,942 個）。
  Unicode 的私用區（Plane 15/16）只有 131,068 個，**不夠**；而且沒有字型畫得出來。
- 所以「一原子一字符」只能做成**兩層**：
  - **高頻原子（前 4,096 個）給一個字符**：覆蓋 70% 的原子出現次數；
  - 其餘用**拼寫逃逸**（escape），例如 `~kāraṇa` 這種「原字照寫」。
- 另一個方向是**再往下拆一層**（詞綴層），把原子數壓到幾千：
  單音節原子只有 19,286 個（7.5%），但佔 19.8% 的出現次數；≤2 音節的有 85,691 個（33.4%）。
  → 先拆到「詞幹＋詞尾」再給字符，字母表會小一個數量級，但要多做一層形態分析。

**結論**：`一個字符`不可能是「一個原子一個字符」（25 萬個字符不現實）；
可行的是「**高頻原子一個字符 ＋ 其餘逃逸拼寫**」，或「再拆一層詞綴」。
數據已經在 `pwa-alphabet.tsv`（前 4,096 名，含次數與詞幹），可以直接拿去配字符。

## 6. 限制與坑

- **pwa 的 hyphen 是「連音前」的寫法**，不是原文切點：`sāpekkhāya → sa-apekkhāya`。
  拿它當「詞件」可以，拿它算原文位置不行。
- **pwa 沒有版本戳**（只有 `pwa(pali words analyzer) | @sunanda generated by ai`），
  換版本後數字會變；重跑時要重算 `pwa-summary.txt`。
- 遞迴**不會無限深**：`MAX_DEPTH=6`，另有 `stack` 防環（pwa 有極少數 A→B→A）。
- 記憶體：這支腳本**刻意不快取**（之前快取一百萬筆把記憶體吃爆）；
  全部直接查 SQLite，40 秒跑完。
- 9.7% 的壞詞件不要拿來訓練／統計；統計時用「詞件是 pwa 詞形」的子集。

## 7. 下一步（建議）

1. 把 `pwa-alphabet.tsv` 的前 N 個原子配上字符（私用區），產生「一字元編碼表」，
   量出 `word → 字符序列` 的平均長度與逃逸率。
2. 對「逃逸」的那 30%，試**詞綴層**（`kāraṇa → kar + aṇa`），看字母表能壓到多少。
3. 附詞（`iti／ca／eva／api`）抽成獨立一層，詞幹本身不要含它們——這樣同一個詞幹
   在不同連聲下會收斂到同一個代碼。

### 8.1 裡面有什麼

### 8.2 資料怎麼挑、怎麼塞進 2 MB

- 詞頻：`data/cs/*.xml` 的正文（去標籤後數字母詞），取前 60,000 個。
- **多階詞**：pwa 的拆法很淺（2 階 10.8%、3 階 0.2%、4 階 25 個），高頻詞幾乎都在 1 階以內，
  所以另外補「有正文次數的 2 階詞（前 24,000）＋ 3 階以上全收」。
- **樹用詞件 id 存**，不存字串：`sabbaññuta[sabbaññu[sabba|ññu]|tā]|dantā` 變成
  `[[12,[[13,[[14],[15]]],[16]]],[17]]`，同樣的資料少 5%。
- **詞形依詞名排序 ＋ 共用前綴壓縮**：每個詞只存「與前一個詞共用幾個字 ＋ 剩下的字」，
  例 `dhammacakka` 之後的 `dhammacakkappavattana` 存成 `[11, "ppavattana", …]`；
  排序本身也讓 gzip 好壓，兩者合起來再省約一成半。
- **整包 gzip ＋ base64 內嵌**（`DecompressionStream('gzip')` 是瀏覽器原生），
  JSON 5.21 MB → gzip 1.44 MB → base64 1.91 MB；開檔時解壓再啟動。
- **索引改成平坦差分編碼**：`{n:[每個詞件幾個詞], d:[詞序差值]}`，取代「一個詞件一個陣列」；
  客戶端第一次用到才展開，並按詞頻排好（畫面「先列高頻」）。這一步讓整包再省 17%。
- 預算：單檔上限 **2 MB**（建置時會檢查）；現在 83,252 詞 = **1,946 KB（95%）**。
- 樹：`out/pwa-tree-all.tsv`（`pwa-tree.ts` 的產物，深度可到 4）。
- 詞件次數：`data/cs-decomp/pwa-atoms.tsv`（出現在多少個 pwa 詞形裡）。
- 全部 inline；沒有任何 `fetch`、CDN、字型檔。

### 8.4 驗收（2026-11-02 實測）

- Edge headless `file://` 截圖：暗色、亮色、4 階詞（`anupādisesaparinibbānañca` → `anupādisesaparinibbānaṃ[anupādisesa[an|upādisesa[upādi|sesa]]|parinibbānaṃ] | ca`）、搜尋（`dhamma` 同時列出詞與詞件）都正常。
- DOM 互動測試（headless 注入點擊）：點詞件、切分頁、點詞列、「多階」排序（4 階排最前）、「顯示更多」都會更新畫面與 `#hash`。
- 建置腳本自動檢查：沒有外部 script／樣式／URL、沒有 `sourceMappingURL`、**不超過 2 MB 預算**。

### 8.5 已知限制

- 「高頻」是**經文語料的詞頻**（`data/cs` 現在是 139 檔、965 萬詞）；pwa 自己沒有頻率。
- 詞件次數 = 「出現在多少個 pwa 詞形裡」，不是經文次數；兩者在畫面上要分清楚。
- pwa 的壞詞件（`dva|ttiṃsa`、`nti|ādi`）照樣會出現；沒有做人工校修。
- 2 階詞在語料裡有九萬個，只收前 24,000；其餘靠搜尋補。
- 需要 `DecompressionStream('gzip')`（Edge／Chrome 80+、Firefox 113+、Safari 16.4+）；
  不支援時頁面會顯示訊息，不會白屏。
- 沒有 guided tour、沒有匯出、沒有深色以外的無障礙測試。
