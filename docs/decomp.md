# 巴利詞的多階拆分（decomp）

> 目標：讓**詞自己帶著拆分信息**——`dhammacakkappavattana` 不是一整團，而是
> `dhamma + cakka + pavattana`；而 `pavattana` 如果本身還能拆，就再拆下去
> （`盟 = 明 + 皿`、`明 = 日 + 月`，而不是一次拆成 `日 + 月 + 皿`）。
>
> 這份只做**從 pwa 出發**的多階表（2026-11-02 起的方向：先不看經文）。
> 經文那邊的補充表見 §5。

## 1. 檔案與指令

```powershell
cd D:\2026\sz
bun run src/decomp/pwa-tree.ts     # 40 秒；記憶體友善（不快取 pwa）
```

| 檔 | 內容 | 大小 |
|---|---|---|
| `data/cs-decomp/pwa-tree.tsv` | **多階樹**（只收深度 ≥ 2 的 105,620 個詞） | 7.5 MB |
| `data/cs-decomp/pwa-atoms.tsv` | 全部原子 ＋ 出現次數 ＋ 詞幹 | 6.3 MB |

| `data/cs-decomp/pwa-summary.txt` | 一行式摘要（給人快速看） | 小 |
| `out/pwa-tree-all.tsv` | 全部 956,729 個詞形的樹（大檔，不進版控） | 38 MB |

樹的字串寫法：`a[b|c]|d` ＝ 第一層是 a、b、d，其中 b 再拆成 b、c。
例：

```

pañcakaṅgoti      2  pañcakaṅgo[pañca|aṅgo] | iti
uttarāsaṅgaekaṃsakaraṇādīsu  2  uttarāsaṅga[uttara|āsaṅga] | ekaṃsa | karaṇa | ādīsu
```

## 2. 結果（956,729 個 pwa 詞形，≥3 字母）

| 深度 | 詞形數 | 佔比 | 意思 |
|---|---|---|---|
| 0 | 169,333 | 17.7% | 原子（pwa 認為不能再拆） |
| 1 | 681,776 | 71.3% | 拆一次（最常見） |
| 2 | 103,253 | 10.8% | 拆兩層 ← **多階真的用得上** |
| 3 | 2,342 | 0.2% | |
| 4 | 25 | 0.003% | |

- 平均每個詞 **2.51** 個原子。
- 原子 **256,387** 個；把 `dhamma／dhammā／dhammaṃ` 這種收成詞幹後 **130,942** 個。
- 詞件不是 pwa 詞形的：**205,227 / 2,117,517（9.7%）**——這是「抓大放小」要放掉的部分，見 §4。

## 3. 找出來的規律

1. **尾巴幾乎都是「附詞」**。最常見的結尾詞件：
   `iti(90,318) eva(28,880) api(26,552) ca(14,811) vasena(13,404) pi(10,975) ti(9,204)`。
   光是 `iti` 一種就佔 9.4% 的詞形——pwa 把 `…nti`、`…mīti` 這種連聲都拆成「詞＋iti」。
   → **附詞（ca／iti／eva／api／pi／vā）應該獨立一層**，不要跟前面的詞混在一起。
2. **開頭幾乎都是前綴或限定詞**：`a(26,982) sa(7,854) mahā(7,083) an(6,717) na(6,562)
   eka(6,278) sabba(6,057) su(5,373)`。`a-`／`an-`／`na-` 是否定前綴，`sa-`／`su-`／`du-`
   是同族前綴，`mahā-`／`eka-`／`sabba-` 是限定成分。
   → 前綴本身是「單音節或雙音節的封閉集合」，很適合當第一層。
3. **深度只到 2**。pwa 的拆法本身很淺：`cakka`、`kāraṇaṃ` 這種它不再拆（雖然詞源上
   `kāraṇa = kar + aṇa`）。所以要「拆到一個字符」，pwa 不夠，得再往下接**詞綴層**。
4. **9.7% 的詞件是壞的**，幾乎都是連聲把字吃掉或加倍：
   `dvattiṃsa → dva|ttiṃsa`（`ttiṃsa` 不是詞）、`puññaphalañca → puññaphala|ca` 沒問題，
   但 `…añca` 這種會被寫成 `…aṃ|ca` 或 `…añ|ca`。**不要為了這 9.7% 改規則**。
5. **原子裡有一批「不是詞」的碎片**：`a`（否定前綴）出現 35,410 次、`sa` 10,446 次、
   `an` 8,457 次、`na` 7,697 次——它們是前綴，不是自由詞。設計字母表時要把它們跟前綴層對齊。

## 4. 「一個字符」的算術（重要）

如果目標是「**每個因子剛好一個字符**」，那字母表要多大？用原子出現次數算：

| 字母表大小 | 覆蓋原子出現次數 |
|---|---|
| 10 | 12.7% |
| 32 | 18.9% |
| 64 | 23.8% |
| 128 | 30.3% |
| 256 | 37.7% |
| 512 | 45.7% |
| 1,024 | 54.0% |
| 2,048 | 62.3% |
| 4,096 | 70.1% |
| 8,192 | 76.9% |
| 16,384 | 82.5% |

- 要 **100%** 一原子一字符，需要 **256,387** 個字符（收成詞幹也要 130,942 個）。
  Unicode 的私用區（Plane 15/16）只有 131,068 個，**不夠**；而且沒有字型畫得出來。
- 所以「一原子一字符」只能做成**兩層**：
  - **高頻原子（前 4,096 個）給一個字符**：覆蓋 70% 的原子出現次數；
  - 其餘用**拼寫逃逸**（escape），例如 `~kāraṇa` 這種「原字照寫」。
- 另一個方向是**再往下拆一層**（詞綴層），把原子數壓到幾千：
  單音節原子只有 19,286 個（7.5%），但佔 19.8% 的出現次數；≤2 音節的有 85,691 個（33.4%）。
  → 先拆到「詞幹＋詞尾」再給字符，字母表會小一個數量級，但要多做一層形態分析。

**結論**：`一個字符`不可能是「一個原子一個字符」（25 萬個字符不現實）；
可行的是「**高頻原子一個字符 ＋ 其餘逃逸拼寫**」，或「再拆一層詞綴」。
數據已經在 `pwa-alphabet.tsv`（前 4,096 名，含次數與詞幹），可以直接拿去配字符。

## 6. 限制與坑

- **pwa 的 hyphen 是「連音前」的寫法**，不是原文切點：`sāpekkhāya → sa-apekkhāya`。
  拿它當「詞件」可以，拿它算原文位置不行。
- **pwa 沒有版本戳**（只有 `pwa(pali words analyzer) | @sunanda generated by ai`），
  換版本後數字會變；重跑時要重算 `pwa-summary.txt`。
- 遞迴**不會無限深**：`MAX_DEPTH=6`，另有 `stack` 防環（pwa 有極少數 A→B→A）。
- 記憶體：這支腳本**刻意不快取**（之前快取一百萬筆把記憶體吃爆）；
  全部直接查 SQLite，40 秒跑完。
- 9.7% 的壞詞件不要拿來訓練／統計；統計時用「詞件是 pwa 詞形」的子集。

### 8.2 資料怎麼挑、怎麼塞進 2 MB

- 詞頻：`data/cs/*.xml` 的正文（去標籤後數字母詞），取前 60,000 個。
- **多階詞**：pwa 的拆法很淺（2 階 10.8%、3 階 0.2%、4 階 25 個），高頻詞幾乎都在 1 階以內，
  所以另外補「有正文次數的 2 階詞（前 24,000）＋ 3 階以上全收」。
- **樹用詞件 id 存**，不存字串：`sabbaññuta[sabbaññu[sabba|ññu]|tā]|dantā` 變成
  `[[12,[[13,[[14],[15]]],[16]]],[17]]`，同樣的資料少 5%。
- **詞形依詞名排序 ＋ 共用前綴壓縮**：每個詞只存「與前一個詞共用幾個字 ＋ 剩下的字」，
  例 `dhammacakka` 之後的 `dhammacakkappavattana` 存成 `[11, "ppavattana", …]`；
  排序本身也讓 gzip 好壓，兩者合起來再省約一成半。
- **整包 gzip ＋ base64 內嵌**（`DecompressionStream('gzip')` 是瀏覽器原生），
  JSON 5.21 MB → gzip 1.44 MB → base64 1.91 MB；開檔時解壓再啟動。
- **索引改成平坦差分編碼**：`{n:[每個詞件幾個詞], d:[詞序差值]}`，取代「一個詞件一個陣列」；
  客戶端第一次用到才展開，並按詞頻排好（畫面「先列高頻」）。這一步讓整包再省 17%。
- 預算：單檔上限 **2 MB**（建置時會檢查）；現在 83,252 詞 = **1,946 KB（95%）**。
- 樹：`out/pwa-tree-all.tsv`（`pwa-tree.ts` 的產物，深度可到 4）。
- 詞件次數：`data/cs-decomp/pwa-atoms.tsv`（出現在多少個 pwa 詞形裡）。
- 全部 inline；沒有任何 `fetch`、CDN、字型檔。

### 9.4 已接進 MVP 的 dpd 第二層（2026-11-02）

按作者指示「dpd 不能照單全收，`sace` 沒必要再拆」，做法是：

1. 只碰 pwa 判斷成**原子**（0 階）的詞；
2. 先過規則（`src/decomp/dpd-comp.ts`）：詞件 ≥2 字母、沒有 `??`、不是 `ka／tā／ti` 這種詞綴、
   不是數詞（`dvādasa`、`pannarasame`… 詞源拆法）、每個詞件都要是字典查得到的詞；
3. 再過人工排除清單 `data/cs-decomp/dpd-exclude.tsv`（`sace`、`dīpa`、數詞…）；
4. 通過的 850 條接成第二層，畫面上標「第二層來自 dpd（詞級複合）」。

| | 數 |
|---|---|
| 候選（pwa 原子且有 dpd comp） | 1,235 |
| 採用 | **850** |
| 排除 | 385（數詞 81、壞詞件 `a/ā/ī/??` 93、接起來就是原詞 45、詞綴 `ka/tā/ti` 65、排除清單 20、詞件不是字典詞 37…） |

例：`tathāgato → tathā + gata`、`gahapati → gaha + pati`、`jetavane → jeta + vana`、
`saddhivihārike → saddhiṃ + vihārika`。

### 9.5 緬文 viggaha 轉寫：pm1 這塊解鎖了（2026-11-02）

作者指路：<https://github.com/myanmaropenwordnet/mya2rom>。看過之後的判斷：

- **那是給緬甸語用的**（MLCTS／IPA；`သ`→`th`、`ည`→`ny`、`ရ`→`y`），不是巴利。

  （約 120 行，含測試：`စက္က→cakka`、`အင်္ကိတ→aṅkita`、`ပဋိစ္စသမုပ္ပါဒ→paṭiccasamuppāda`）。

**結果**（`bun run src/decomp/pm1-viggaha.ts`）：

| | 數 |
|---|---|
| pm1 有 viggaha 的條目 | 154,229 |

### 9.6 pm1 接進 MVP：第三層（2026-11-02）

緬文轉寫打通之後（§9.5），pm1 的 viggaha 接成第三層。**但不能照單全收**：
viggaha 是「詞解析」，一半是文法派生（`bhogo → bhuja + ṇa`），不是複合詞。

規則（`src/decomp/pm1-comp.ts`）：

1. 詞件 2–4 件、每個 ≥2 字母、都是字典詞；
2. 不能是詞綴（`ṇa`、`ti`、`ta`、`ya`、`ṇika`…）；
3. 第一件不能就是原詞（那是派生不是複合）；
4. 不是數詞；
5. **每個詞件至少要在 50 個 pwa 詞形裡出現過**——這一條最關鍵：詞根／詞尾的次數都很低，
   常用詞才會過關。

| | 數 |
|---|---|
| 候選（MVP 原子且 pm1 有 viggaha） | 17,295 |
| 採用 | **1,004** |
| 排除 | 16,291（壞詞件 5,221、詞綴 `ṇa/ti/ta/ya…` 5,000+、太少見 1,200+…） |

例：`anulomato → anu + loma`、`anuppannāya → na + uppanna`、`abhirūpe → abhi + rūpa`。

另外，**原子詞（pwa 不再拆）補「詞幹」**：14,115 個 ≥8 字母的原子詞，畫面上多一行
「詞幹 xxx」（例 `abbhantarato → 詞幹 abbhantara`），讓初學者至少有字典形可查。

### 9.7 詞幹＋中文：讓「每個詞都有東西看」（2026-11-02）

作者定的目標是「初學者每詞可拆、降低記憶量」。三層拆分（pwa／dpd／pm1）之後，還有一大批
pwa 判成原子的詞沒有東西可看；這一輪補兩樣：

1. **詞幹**：原子詞都給 pwa 的字典形（23,294 個），例 `abbhantarato → 詞幹 abbhantara`、
   `bhagavato → bhagavant`。對初學者，這比「再拆一層」實用——先知道查哪個字。
2. **詞件中文**：常用詞件（在 pwa 出現 ≥50 次）接 OpenTipitaka 的 AI 中文詞典，
   4,593 個詞件有中文。畫面上詞件後面直接寫意思：
   `tathāgato → tathā（如此、如是）＋ gata（已去的、已達到的）`。

**覆蓋率**：72,742 個詞裡，95.4% 至少有「詞件」或「詞幹」其中一樣；
其餘 4.6% 是本身的字典形就是它自己（真的單純詞）。

**pm12e 前綴層試過，不採用**：它的 `[Na+B]` 拆法多半是動詞派生（`abhi + hara + tvā`），
詞件是詞根不是詞；用「前綴白名單＋詞件 ≥50 次」過濾後，MVP 的 26,871 個原子詞只剩
**100 條**可用，不值得為它加一層。

### 9.8 整詞中文：讓每個常見詞至少有一句（2026-11-02）

上一輪只有「詞件」有中文；這一輪把 `opentipitaka_dict_zh` 的**整詞釋義**也放進來，

| | |
|---|---|

### 9.9 讀經文模式（2026-11-02）

初學者不是查詞，是讀句子。所以在「詞表」之外加了一個「讀經文」模式：貼一段巴利文，
每一詞都可以點，右邊（或下面）直接顯示中文。

- 開頭那段 DN1 的實測：**84 / 92 詞認得（91%）**；開啟「每詞顯示中文」後，
  366 個詞有行間中文。
- 認不得的多是專名（`suppiyo`）、標題（`(sīlakkhandhavaggapāḷi)`）與罕見長複合詞。

**順手修了一個大漏洞**：`pwa-tree.ts` 原本只收 ≥3 字母的詞形，所以 `ca`、`me`、`te`、
`ye`、`so`、`na` 這些最常見的虛詞根本不在 MVP 裡。改成 ≥2 字母後重建，同一段經文的
覆蓋率從 **79% → 91%**。

### 9.10 讀經文：就地彈出＋不認得的詞（2026-11-02）

上一輪的讀經模式，點詞會跳回詞表，讀到一半就斷了；這一輪改成**就地彈出**：

- 點詞 → 右下角浮出：詞義、拆解（可點）、詞件中文、「在詞表打開 →」；`Esc` 或點空白處關閉。
- 讀經時，**不認得的詞**收集在下方（例：`suppiyopi ×2`、`ekarattivāsaṃ ×2`），可以一鍵複製，
  當作下一批要補的詞。
- 原子詞不再顯示「自己拆自己」的單節點樹（之前 `bhagavā` 會出現一個 `bhagavā` 的詞件）。

實測（DN1 樣本）：110 / 121 詞認得（91%），不認得 8 個。

### 9.11 專名表與「不認得的詞」下載（2026-11-02）

### 9.13 格式瘦身：原子詞不存樹（2026-11-02）

原子詞（pwa 不再拆）的樹只有一個節點——它自己。之前每筆都存 `[id]`，25,975 筆重複。
改成**原子詞不存樹**，客戶端用 `atomByName` 還原：

```js
function treeOf(idx) {
  if (WORDS[idx].t) return WORDS[idx].t;
  var id = atomByName.get(WORDS[idx].w);
  return id == null ? [] : [id];
}
```

省下 **87 KB**（2,030 → 1,943 KB）。省下來的空間給整詞中文：9,000 → **13,301** 個詞
（預算 41,000 → 64,000 字），檔案回到 1,985 KB（97%）。

### 9.14 詞性：只從字典的語法欄位來（2026-11-02）

作者指示：「內容深度之後再做，不能猜，要從字典來。」所以這一輪只做**字典已經寫明的東西**：

`dpd` 的 grammar 第一行（`masc`、`fem`、`nt`、`adj`、`pr`、`pp`、`ind`、`pron`、`card`…）
折成 8 類（名詞／形容詞／動詞／分詞／不變詞／代名詞／數詞），逐詞一個字元存成 `pos` 字串
（與 words 同序，gzip 後約 22 KB）：

| 詞性 | 詞數 |
|---|---|
| 名詞 | 29,859 |
| 形容詞 | 12,575 |
| 動詞 | 9,781 |
| 分詞 | 5,945 |
| 不變詞 | 2,654 |
| 代名詞 | 1,776 |
| 數詞 | 1,936 |
| **沒有（dpd 查不到）** | **9,693（13.1%）** |

查不到的就留白，**不推測**。畫面例：`bhagavā` → 「名詞 · 原子 · 詞幹 bhagavant · 世尊」。

**格位、時態不做**：那要嘛字典有寫（dpd 的 grammar 只有詞性與部分語法，沒有格），要嘛得自己推，
後者就是「猜」，違反指示。等有字典來源（例如 PTS PED 的語法縮寫、或緬甸辭典的格位說明）再說。

### 9.15 格位／時態：字典有表，但單看字典不夠（2026-11-02，暫緩）

順著「要從字典來」去找，找到一樣東西：**`pe5` 是字典庫裡的語法表**（330,972 列），
鍵是詞形，值是語法碼：

```
buddho     → m.s.nom.            （陽性單數主格）
dhammaṃ    → m.s.acc.            （陽性單數對格）
bhagavato  → m.s.dat.#nt.s.dat.#m.s.gen.#nt.s.gen.   ← 一形多格
gacchati   → Pr.Para.s.3rd.      （現在式第三人稱單數）
bhavissati → Fut.Para.s.3rd.
```

MVP 的 74,219 個詞裡有 **25,105 個（33.8%）** 查得到語法碼，格式乾淨、可以直接翻成中文
（陽性單數主格、現在式第三人稱單數…）。

**但作者決定暫緩**：巴利有大量「一形多格」（`bhagavato` 同時是與格與屬格），
光靠字典只能列出所有可能，要判斷「這一句是哪一個」得看句子上下文——那是另一個工程。

所以這一輪把已經做進去的語法欄位**撤掉**，只留詞性（名詞／動詞／形容詞…，那是詞類不是格位）。
`pe5` 的探測結果留在這裡，等要做句法時直接接。

### 10.2 bigram 值不值得？（2026-11-02）

問題：詞元拆好之後，要不要對**極高頻詞元**改用 bigram，縮短 posting list？
`bun run src/decomp/bigram-stats.ts`（5 本書、34.8 萬詞元、31,505 行）：

| | token | posting | 最長 posting | gzip |
|---|---|---|---|---|
| unigram | 19,908 | 306,840 | **6,133** | 736 KB |
| bigram（全部） | 76,055 | 302,666 | 1,491 | 874 KB（+19%） |
| 前 5 個改 bigram | 23,094 | 307,067 | 2,890 | 753 KB（+2%） |
| 前 10 個 | 25,133 | 307,115 | 2,338 | 762 KB（+4%） |
| **前 20 個** | 28,402 | 309,405 | **1,517** | 781 KB（**+6%**） |
| 前 50 個 | 33,462 | 309,552 | 1,491 | 800 KB（+9%） |

**結論**：

1. **最長的 posting 只由二十來個詞元決定**（`kho 6,133`、`ti 5,131`、`na 4,158`、`ca 4,055`…）。
   只把前 20 個改成 bigram，最長 posting 就從 6,133 掉到 1,517（−75%），代價是索引 +6%。
2. **全部改不值得**：bigram 全部化只再多降一點（1,491），但 token 變 3.8 倍、索引 +19%；

3. 查單一虛詞時要聯集它的所有 bigram（`kho` → 452 個），所以 bigram 化只該用在

實務建議：**stoplist 優先，bigram 其次**。先用 stoplist 把那 20 個排除（§10.1），
posting 總量就降了兩成；真的還要縮短 posting 時，再對剩下的長尾詞元做 bigram。

   > 這些內容詞被踢出索引（dpd 用 `idiom` 標慣用語，不是詞類）。修正後 stoplist 從 62 降到 51，

### 11.2b bigram 的結論改變了

原本以為要對「極高頻詞元」做 bigram；把虛詞判斷修好（`na`、`api`、`a` 也進 stoplist）之後，

而那些正是使用者要查的詞。把它們 bigram 化，查 `dhamma` 就得聯集上千個 bigram，得不償失。

所以順序是：**stoplist 先做（免費、降 29% posting），bigram 不必做**。

### 11.3 還沒解決的

  還在索引裡，好處是它們的 posting 很短，影響不大。
- **索引端要改**：這份政策要真的生效，得改 `adb-converter` 的打包／索引路徑（不在這個工作區）。

### 11.4 整詞次要索引：不便宜（2026-11-02）

拆詞之後查不到「某個特定詞形」（`tathāgatassa`），所以想加一個「整詞 → 行號」的次要索引。

|---|---|---|---|---|
| 主（詞件→詞幹） | 9,175 | 206,163 | 423 KB | — |
| 次（整詞） | 27,707 | 236,203 | 564 KB | +133% |

**結論：整詞查詢不便宜。** 整詞索引的 token 幾乎和拆詞後一樣多（27,707 vs 9,175），
posting 也幾乎一樣多——所以「主＋次」等於把索引加倍（+134%），比混合索引（+105%）還貴。

也就是說：

- 要**精確詞形**（查 `tathāgatassa` 只找這個字）→ 得付 +105～134% 的代價；

而不是另建一份整詞索引——這樣既保留召回，也不需要第二份 postings。

### 10.5 組合詞裡的屈折信息丟失（2026-11-02，作者指正）

作者指出：`dhamma` 頻次高，是因為**組合詞（六離合釋）裡非末位成員的屈折信息會丟失**，
詞形不能完全反映文法。量了一下（`bun run src/decomp/compound-ratio.ts`）：

| | posting | 佔比 |
|---|---|---|
| 來自**組合詞成員** | 7,600,641 | **51.8%** |
| 來自**獨立出現的詞** | 7,070,586 | 48.2% |

幾個 token 的組成：

| token | 組合詞成員 | 獨立詞 | 組合佔比 |
|---|---|---|---|
| `dhamma` | 65,646 | 81,411 | 45% |
| `attha` | 70,118 | 41,435 | 63% |
| `eva` | 170,937 | 14,397 | 92% |
| `api` | 174,144 | 4,022 | 98% |
| `a` | 165,900 | 2,503 | 99% |
| `ādi` | 134,091 | 6,176 | 96% |
| `hoti` | 14,764 | 114,574 | 11% |

**這件事的三個結論**：

1. **詞幹 token 只是把「組合詞已經在做的事」推廣到獨立詞**。組合詞裡的 `dhamma-` 本來就不帶格位，
   我們把獨立的 `dhammo / dhammaṃ / dhammassa` 也收成 `dhamma`，token list 才一致（−83%）。
2. **token 頻次 ≠ 文法頻次**。`dhamma` 的 147,057 個 posting 裡，45% 是組合詞成員——
   那些成員的格位在詞形上根本不存在。所以不能從 token 頻次回推「dhamma 當名詞出現幾次」。
3. **也不能從 token 推斷格位**（與 §9.15 一致）。要恢復組合詞成員的格位，只能靠字典的
   viggaha（例如 `dhammacakka = dhammassa cakkaṃ`），那是另一個工程。

對索引設計的意義：**B3 是對的方向**——它讓獨立詞與組合詞成員用同一種 token，
減少重複；代價是查不到特定屈折形，而那個代價本來就有一半存在於組合詞裡。

### 11.5 片語查詢原型：能找回詞形，但位置索引更貴（2026-11-02）

`bun run src/decomp/phrase-query.ts`（5 本書）。把 token 的位置（不是行號）也存下來，
查 `tathā gata` 就是「連續兩個詞件」：

| | token | 位置 | gzip |
|---|---|---|---|
| 行索引（§11.4 主索引） | 9,175 | 206,163 | 423 KB |
| **位置索引** | 9,101 | 357,331 | **1,078 KB（+155%）** |

查詢對照（片語 vs 表面詞前綴）：

```
dhammacakka   片語 9 次   ＝  整詞 9 次     ✔
tathāgata     片語 546 次    整詞 292 次    ✘ 過度匹配
sāvakasaṅgha  片語 46 次     整詞 0 次       （跨書邊界，樣本外）
```

**兩個結論**：

1. **片語查詢可行**——`dhammacakka` 完全對上。
2. **但代價比整詞索引更高**：位置索引 +155%，整詞次要索引 +134%。兩條路都比「不用」貴一倍以上。
3. **精度還要調**：`tathāgata` 過度匹配（546 vs 292），原因是同一個詞件對（`tathā`+`gata`）
   會由不同的表面詞產生（例如 `tathāgataṃ`、`tathāgatassa` 之外，還有拆法產生的變體）。
   要精準，得在片語之外再核對「詞界」——那就等於把整詞資訊存回去了。

**所以「精確詞形查詢」沒有便宜的解法**：要嘛加一份整詞索引（+134%），要嘛存位置（+155%）。
如果作者只在意召回（查 `dhamma` 找到 `dhammaṃ`），B3 就夠了。

### 10.6 token list 稽核：76% 不是詞典詞頭，但都是合格詞幹（2026-11-02）

`bun run src/decomp/token-audit.ts`：把 155,334 個 keep token 拿去對詞典（pwa 956k ＋ dpd 74k 詞頭）。

| | 數量 | 佔比 |
|---|---|---|
| 不是詞典詞頭的 token | 118,523 | 76.3% |
| 它們承載的 posting | 545,873 / 10,424,664 | **5.2%** |

看起來嚇人，但看內容就知道沒問題：

```
rājan(25,733)  attan(9,927)  brahman(7,792)  saññin(4,450)
mahant(4,073)  sant(3,814)   vādin(3,383)    gāmin(3,215)
tvam(3,185)    hatthin(3,187)
```

這些是 **-n / -nt 結尾的詞幹**（`rājā` 的詞幹是 `rājan`、`attā` 是 `attan`、`brahmā` 是 `brahman`），
字典列的是主格形（`rājā`），所以對不上詞頭——但語言上它們是對的。

**兩個推論**：

1. **token list 的精度沒問題**：76% 只是「詞幹形 ≠ 詞頭形」，而且只佔 5.2% 的 posting。
2. **查詢端必須做同樣的詞幹化**：使用者查 `rājā`，要正規化成 `rājan` 才找得到；
   否則 76% 的 token 是查不到的。這要寫進規格（§12.6）。

### 12.6 查詢端的正規化（重要）

索引端的 token 是「詞件→詞幹」，查詢端必須套**同一條管線**，否則查不到：

```
使用者輸入 rājā  →  詞形 rājā  →  pwa 詞件（單一）  →  詞幹 rājan  →  查 token rājan
使用者輸入 dhammacakkaṃ  →  詞件 dhamma + cakkaṃ  →  詞幹 dhamma + cakka  →  片語查詢
```

不做這一步，76.3% 的 token（詞幹形，例如 `rājan`、`attan`）永遠不會被查到——
它們只佔 5.2% 的 posting，所以影響不大，但那是「查得到 / 查不到」的差別。

查詢端需要的資料：`out/pwa-tree-all.tsv`（詞形→詞件）＋ `data/cs-decomp/pwa-atoms.tsv`（詞件→詞幹）。

### 10.7 詞幹不一致：322 組（6.7% 的 posting）（2026-11-02）

pwa 給的是「每個詞形自己的詞幹」，同一個詞可能因此有兩個 token：

| 較短的 | 較長的（-n / -nt 詞幹） |
|---|---|
| `rāja` 15,554 | `rājan` 25,733 |
| `atta` 50,981 | `attan` 9,927 |
| `brahma` 127 | `brahman` 7,792 |
| `saññi` 71 | `saññin` 4,450 |
| `hatthi` 1,061 | `hatthin` 3,187 |

共 **322 組**，合計 **703,289 個 posting（6.7%）**。對索引的影響：同一個詞被拆成兩個 token，
召回與 token 數都吃虧；查 `rājā`（→ `rājan`）找不到 `rāja` 那邊的 15,554 次。

**有字典來源可以修**：dpd 的詞條直接寫出「詞基 + 語尾」——

```
rājā   →  rāja + ā          （dpd 寫的是 rāja，不是 rājan）
mahā   →  mahanta + ā
hatthī →  hattha + ī
```

所以正規化的路線是：

```
詞形 → pwa 詞幹 → 反查 lemma（pwa 反轉）→ dpd 的詞基 → canonical token
```

這樣同一組會收斂成一個 token（`rāja`、`mahanta`…），而且是字典寫的，不是猜的。
還沒實作——下一輪可以把 322 組先套一遍，量 token 與 posting 的變化。

**實作結果（同日）**：`bun run src/decomp/stem-canonical.ts`。

- dpd 有「詞基 + 語尾」的詞條 **36,534** 條（在內容的後幾行，不在第一行）；
- 詞幹→詞基對映 **5,383** 組；
- 套下去 token 155,334 → **153,398（−1.2%）**，posting 不變；
- 322 組詞幹分歧只收斂了 **8 組（2%）**——dpd 的詞基欄位覆蓋不到大部分詞幹。

**結論：不值得在索引端做詞幹收斂。** 收益只有 1.2%，而且要維護一條「lemma→詞幹→詞基」的鏈。

更好的做法是**查詢端展開**：查 `rājā` 時同時查 `rāja` 與 `rājan`（兩個 token 的 posting 取聯集），
索引不動、召回補回來，成本只在查詢時。這要等索引端支援多 token 查詢（§12.6 一起做）。

### 11.6 逐次詞性決定 stoplist（介面已備，等資料）

**問題**：字典只能說「這個詞有幾種詞類」，不能說「這一句是哪一種」。現行 stoplist 因此
會整詞停用 `na`、`sabba`、`tad` 這種「有時候是虛詞、有時候是內容詞」的 token。

**解法**：komyoji 的來源（㊣巴利／㊔名詞／㊒動詞）是**逐詞**標記，把它整理成
`data/cs-decomp/pos-distribution.tsv`：

```
word	pos	count
na	ind	152813
na	noun	179925
sabba	adj	96000
sabba	pron	54000
```

`pos` 用 dpd 的寫法；虛詞類＝`ind/adv/conj/prep/prefix/pron/neg/part`，其餘算內容詞。

**規則**：`posting ≥ 10,000` 且**虛詞佔比 ≥ 90%** 才停用；否則保留。這樣 `na` 若有一半是名詞，
就不會被整詞踢出索引。

**介面**：`bun run src/decomp/pos-stoplist.ts`（`--write` 才寫檔）。
資料還沒到時，它會用 dpd 的多類標記造一份**模擬**分佈，驗證邏輯而不污染政策：

```
現行政策：token 155,396、stop 51
（模擬）新政策：stop 40，由停用改回保留 11 個：
  na(50%) a(0%) sabba(50%) ayaṃ(50%) pubba(50%) tato(50%) tad(50%) sammā(50%) antara(50%) yeva(50%) esa(50%)
```

這 11 個就是「字典說它是虛詞，但可能有一半是內容詞」的名單——等 komyoji 的逐次標記來裁決。

### 11.7 索引該聽標記的，還是 pwa 的？（2026-11-02）

`data/cs` 的每個組合詞都有 `<詞 b="rAj|ghM" j="0">rājagahaṃ</詞>`——**adb 自己的分段**。
問題：索引要用這個，還是繼續用 pwa 的樹？

`bun run src/decomp/markup-vs-pwa.ts`（437,546 個標籤）：

| | 數量 |
|---|---|
| 標籤 | 437,546 |
| pwa 也有樹 | 356,095 |
| pwa 沒樹 | 81,451 |
| 兩者**相同** | 213,019（**59.8%**） |
| 兩者不同 | 143,076（40.2%） |

不同的例子（左邊標記、右邊 pwa）：

```
abhidhammatthasaṅgaho   abhidhamma+attha+saṅgaho  ／ abhi+dhamma+attha+saṅgaho
akusalacittaṃ           akusala+cittaṃ            ／ a+kusala+cittaṃ
lokuttarañceti          loku+ttarañ+ce+ti         ／ loka+uttara+ca+iti
nibbānamiti             nibbāna+miti              ／ nibbānaṃ+iti
```

兩種都有對有錯：標記把 `akusala` 保持完整（比 pwa 的 `a+kusala` 好），
pwa 把 `lokuttarañceti` 拆成 `loka+uttara+ca+iti`（比標記的 `loku+ttarañ` 好）。

**但從 token 經濟看，答案很清楚**：

| 分詞來源 | token | posting |
|---|---|---|
| pwa（現行） | **153,776** | 10,925,973 |
| 標記 | 160,416（+4.3%） | 11,001,027 |
| 標記再用 pwa 細分 | 158,340（+3.0%） | 11,171,216 |

**結論：索引用 pwa，標記留給顯示。** 標記是為了「讀者看到什麼」，不是為了「索引收斂」；
用它反而多出 4.3% 的 token（`abhidhamma` 這種大詞件與 pwa 的 `abhi+dhamma` 並存，
同一個詞在索引裡就有兩種切法）。

若要讓兩者一致，方向應該是**把標記改成 pwa 的切法**（顯示端），而不是把索引遷就標記。

### 10.8 大 token 是怎麼來的（2026-11-02）

`bun run src/decomp/token-sources.ts`：把 posting 拆回「貢獻它的詞形」。

```

  ti 337,563  nti 94,822  iti 11,627  tiādi 10,753  hotīti 7,796 …
```

三個結論：

1. **長 posting 是詞幹化的正常結果，不是錯誤**：`dhamma` 的 147,057 次裡只有 0.4% 是
   `dhamma` 本身，其餘是 `dhammaṃ / dhammā / dhammo / dhammassa…`——這正是我們要的收斂。
2. **`iti` 的 74 萬次來自 `ti`（337k）與 `nti`（95k）**：pwa 把 `ti`、`nti` 都當成 `iti` 的

3. **`ti` 這個 token 是數詞「三」**（`tayo`、`tisso` 的詞幹），不是虛詞 `ti`（後者已收在 `iti`）。
   查 `ti` 會得到數詞，查不到虛詞——這是詞幹化的副作用，值得在規格裡註明。

### 15.5 一形多義：token 是詞幹字串的桶子

`bun run src/decomp/homograph.ts ti a`：

```
=== token ti：32,791 次、404 個詞形 ===
  tīṇi   12,369  num265      tayo  6,902  num428,pron2
  tisso   2,622  num279,n34  tīsu  2,360  num25
=== token a：168,403 次、32,496 個詞形 ===
  a         2,494  ind209     akusalā   2,445  adj159
  akusalaṃ  1,747  adj75      abhāvato  1,490  （komyoji 無）
```

兩件事：

1. **token 是「詞幹字串的桶子」，不是「一個詞」。** `a` 這個桶裝了 32,496 個詞形——
   幾乎每一部 `a-` 開頭的否定複合詞（`akusala`、`abhāvato`…）的第一個詞件都是它。
   所以 `a` 的 168,403 次不是「`a` 這個詞出現 16 萬次」，而是「否定前綴出現在 16 萬次」。
2. **一形多義不能用詞形判斷。** `ti` 可以是虛詞（`iti` 的連音）、也可以是數詞
   （`tayo/tisso` 的詞幹）。兩個用法被 pwa 分到不同桶（`iti` 與 `ti`），
   但那只反映切詞慣例，不反映「這個形是哪一種功能」。

對索引的意義：

- **stoplist 的判定是「字串該不該被搜尋」，不是「這個詞是不是虛詞」。**
  `a` 這個字串搜下去是 16 萬筆前綴命中，沒有檢索價值——所以停用（但因為它是前綴，
  停用會讓 `akusala` 少一個可查詞件，所以最後選擇保留，見 §11.2 的修正）。
- **要真的按「功能」索引，就得把桶子拆開**（`ti#num`、`ti#ind`），
  那需要逐次的詞性標記（komyoji 有），成本是 token 變多。
  這一條先不做，記在這裡。

### 15.7 一形多義能不能拆開？（2026-11-02 晚，量測結論）

作者問：有沒有把握用「幾種形」把一形多義簡化成一個形一個義？量了四件事。

**一）形層：大部分形本來就單義**

|---|---|---|---|
| 詞性 | 45,105（96.4%） | 605 | 1,077（2.3%） |
| 格位 | 40,177（86.0%） | 1,308 | 4,607（9.8%） |

**二）逐次（同一個形在不同句子）對不上**

`align.tsv` 有 138,288 個句子對位，但逐**詞**比對：

| 方法 | 對上的詞 |
|---|---|
| 按詞序（第 k 詞 ↔ 第 k 詞） | 22.3% |
| LCS 序列比對 | 27.3% |

> **2026-11-02 修正（作者指正）**：komyoji 的巴利底本**就是 VRI**，只是保留 variant。
> 所以上面「底本不同」的說法是錯的。實際差異在**轉換層**：標題寫法（我們用括號短題、
> 他們用完整標題）、段號標記（`1.` vs `1`）、大小寫（`Evaṃ` vs `evaṃ`）、
> 以及連音切法（`ekarūpampi` vs `ekarūpaṃ pi`）。
>
> 這意味著逐次對位**不是不可能**，而是我用的 `align.tsv` 只到塊.段層、
> 又把標題行對錯，才讓比對率掉到 22–27%。正確做法是以正文的罕見詞序列當錨點，
> 錨點之間再做序列比對（見 §15.8 的待辦）。

**三）所以能做到什麼**

- ✅ **形層消歧**：96.4% 的形只有一種詞性，可直接定；已在 §15.6 做了 `詞幹#詞性`（+3.9% token）。
- ✅ **安全邊界**：多值但主導 ≥90% 的形（POS 605 個）可以指派，錯率 <10%。
- ❌ **逐次消歧**：`te`（主 2,590／属 917／対 333…）、`tassa`（属 1,880／与 225）這種，
  沒有對位就無法判斷某一次是哪一格。

**四）一個實作陷阱**

試著把「單一格位的形」的格位也加進 token 時，出現 `iti#ind#主` 這種東西——
`ti` 這個形在 komyoji 被標成主格名詞，但我們的 stem 是 `iti`、詞性來自 dpd 的 `ind`。
**兩個特徵來自不同來源就會互相矛盾**。要加格位，必須同一個來源同時給詞性與格位，
而且只對名詞類的形使用。

結論：一形一義在**形層**可行（POS 已經做），在**逐次層**不可行。
要突破，得請 komyoji 用他們的文法**直接標註我們的底本**（而不是對位兩份不同的巴利）。

### 15.20 一形多義的分佈：八成其實是「一形一義」（2026-11-03）

### 15.23 komyoji 不是金科玉律（2026-11-03）

作者提醒：komyoji 是十幾年的累積，越做越好（dn、mn、sn、an…），早期錯誤難免。
所以我們不把它當真理，只當「目前最好的證據」。

`bun run src/decomp/komyoji-quality.ts` 量了兩件事：

**一）同一本書內的自我一致性**（每個形出現 ≥5 次時，最常見格位的佔比取平均）

| 書 | 標註詞 | 一致性 |
|---|---|---|
| dn1 | 17,787 | 94.8% |
| mn1 | 26,187 | 92.4% |
| sn3 | 19,432 | 95.5% |
| an10 | 16,514 | 94.2% |
| cp | 3,044 | 87.6% |
| thig | 4,550 | 90.1% |

範圍 87.6–96.3%，沒有明顯的「越早越差」趨勢（dn 反而高於 an 的部分）。

**二）與 pe5（獨立語法表）的一致率**：91.3–93.5%，各書接近。

**怎麼用**：

1. **不宣稱正確**：詞頁寫「格位分佈：属 69% · 与 31%（樣本 1,414 次）」，不是「屬格」。

3. **樣本數是誠實的刻度**：1,414 次的比例比 5 次的可信；低於 5 次的不顯示。

這一節的結論寫給未來的自己：**kmj 的標註是「目前最好的證據」，不是真理。**
當它有更好的版本時，重跑 `align-seg2.ts` 與 `build-index.ts --case` 即可。

作者指出的例子：梵語 **dvīpa**（島）與 **dīpa**（燈）是兩個詞，巴利語合流成 **dīpa**。

查證（wisdomlib.org）：

- PTS《巴利英詞典》把 `dīpa` 分成**三個獨立詞條**：
  1. `Dīpa 1`＝燈（Ved. dīpa，源自 √dīp「燃燒、發光」）；
  2. `Dīpa 2`＝島、洲、庇護所（**Ved. dvīpa ＝ dvi + ap，字面「兩重水之間」**）；
  3. `Dīpa 3`＝豹皮（及其裝飾的車）。
- 梵語詞典（Monier-Williams 等）：`dīpa` 只有「燈／光」；`dvīpa` 才是「島」——**兩個詞並未合流的是梵語，合流的是巴利語**。
- 中文詞典（`opentipitaka_dict_zh`）已完整收錄三義：`1. 灯`、`2. 岛`、`3. 豹皮`。

**語料實證**（`data/cs`）：`dīpa` 名詞形共 **782 次**，兩義都出現：

```
燈：dīpe jalite（燈亮著）、ekaṃ dīpaṃ jāletvā（點一盞燈）、dīpassa vaṇṇa…
島：dīpaṃ viya ca aṇṇave（如海中之島）、taṇhākkhayaṃ dhuvaṃ dīpaṃ（涅槃為穩固之島）
```

**與 `te` 的差別**：

| | `te` | `dīpa` |
|---|---|---|
| 性質 | 語法同形（一個詞位、多種格位） | **詞彙合流（兩個詞位合成一個形）** |
| 能否用上下文分 | 分佈可以量化（主 60%／属 21%…） | 不能：要看**語意**，沒有語意標註 |
| 目前的處理 | 格位分佈＋上下文提示 | **列出所有義項**（3,471 個多義詞） |

**MVP 的修正**：之前詞頁只顯示中文詞典的**第一行**，所以 `dīpa` 只看到「灯」。
現在多義詞會列出全部義項（2–5 義，共 3,471 個詞），`dīpa` 顯示：

```
1. 灯 指照明的器具、油灯或光亮。
2. 岛 指被水环绕的陆地、洲或陆地…引申指依靠处、庇护所…
3. 豹皮 指豹皮或虎皮…
```

**dpd 的缺口**：dpd 對 `dīpa` 只寫「lamp; light」，沒有島的義項——單靠 dpd 會漏義。
這是「多個詞典互相補位」的又一個例子：dpd 給詞性與拆法，中文詞典給義項，PTS 給詞源。
